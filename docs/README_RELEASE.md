# Выпуск релиза

Готовые программы для Windows, macOS и Linux собирает GitHub. Вы запускаете одну команду, и
примерно через 15 минут на странице [релизов](https://github.com/rvburov/backup-desktop-app/releases)
лежат четыре файла с номером версии в имени. На своей машине собирать ничего не нужно.

## Как выпустить версию

```bash
# 1. Описать изменения в секции «## [Не выпущено]» файла
#    scripts/github-release/release-history.md. Одна запись — одна строка.

# 2. Закоммитить и отправить все на GitHub, дождаться зеленых тестов (Actions → Tests).
git push origin master

# 3. Выпустить. На Windows команда запускается в Git Bash.
scripts/github-release/release.sh 9.0.1
```

Скрипт проверит предусловия, прогонит тесты, покажет план и спросит подтверждение. Дальше он
все делает сам:

| Что делает | Где |
| --- | --- |
| `VERSION` → 9.0.1 | `backup_app/backend/constants.py` |
| бейдж → `version-9.0.1-blue` | `README.md` |
| «## [Не выпущено]» → «## [9.0.1] — дата», над ней новая пустая «Не выпущено» | `scripts/github-release/release-history.md` |
| коммит «Выпуск версии 9.0.1» | git |
| аннотированный тег `v9.0.1` | git |
| `push origin master`, затем `push origin v9.0.1` | GitHub |

Push тега запускает [release.yml](../.github/workflows/release.yml), и дальше работает GitHub.
Обычный `git push` релиз не запускает: не каждый push — новая версия.

Полезные ключи:

```bash
scripts/github-release/release.sh 9.0.1 --dry-run      # проверки, тесты и план выпуска; файлы не меняются
scripts/github-release/release.sh 9.0.1 --skip-tests   # без pyflakes и pytest
scripts/github-release/release.sh 9.0.1 --allow-dirty  # разрешить незакоммиченные правки
```

С `--dry-run` без сети сверка с GitHub пропускается с предупреждением. С `--allow-dirty` тесты
идут по рабочему дереву, а в коммит выпуска попадают только три файла выпуска, вместе с их
незакоммиченными правками.

Python для тестов скрипт ищет так: переменная `PYTHON`, затем `venv` или `.venv` в корне
проекта, затем `python3` и `python`. В нем должны стоять пакеты из `requirements.txt`.

### Выпуск версии, которая уже записана в коде

Номер, равный `VERSION` в коде, скрипт принимает, если тег этой версии свободен. Так версию
выпускают заново после [отмены релиза](#отменить-релиз): коммит «Выпуск версии 9.0.1» и секция
`## [9.0.1] — дата` в истории релизов остаются, скрипт берет описание из этой секции, ставит в ее
заголовок сегодняшнюю дату и создает тег. Записи в «Не выпущено» при этом надо перенести в секцию
версии: если записи есть в обеих секциях, выпуск не начнется.

### Нумерация версий

X.Y.Z: **X** — большие изменения, после которых прежняя версия может не понять новые
настройки; **Y** — новые возможности; **Z** — исправления. Номер в коде хранится в одном месте,
`VERSION` в `backup_app/backend/constants.py`. Тег `v9.0.1`, заголовок релиза
`BackupApp 9.0.1`, коммит «Выпуск версии 9.0.1».

## Что проверяется до выпуска

Любая непройденная проверка останавливает `release.sh` до первой правки файлов:

1. Версия в формате `X.Y.Z`. Суффиксы вида `9.0.1-rc.1` не поддерживаются: дефис разделяет
   поля бейджа shields.io, и бейдж сломался бы.
2. Текущая ветка `master`, рабочее дерево чистое.
3. Локальная `master` совпадает с `origin/master`: все отправлено на GitHub.
4. Тег не занят ни у вас, ни на GitHub.
5. Новая версия не меньше текущей.
6. Версия в коде, бейдж README и история релизов согласованы, и у новой версии есть описание.
7. `pyflakes` и `pytest` проходят.

Локально тесты идут только на вашей системе. На GitHub они идут на Windows, Linux и macOS:
в Tests при каждом push и еще раз в `release.yml` перед сборкой. Но тест, который упал уже после
тега, означает перевыпуск с переносом тега, поэтому до `release.sh` дождитесь зеленого Tests.

После правки файлов скрипт еще раз сверяет версию. Если эта сверка не пройдет, правки останутся
в рабочем дереве: посмотрите их в `git diff` и откатите или закоммитьте.

## Что происходит на GitHub

| Этап | Где | Что делает |
| --- | --- | --- |
| Проверки | Ubuntu | тег в формате `vX.Y.Z`, совпадает с версией в коде, бейдже README и истории релизов и стоит на коммите из `master`; pyflakes |
| Сборка | 4 машины параллельно | тесты, сборка PyInstaller, проверка собранного, проверка запуска, упаковка |
| Публикация | Ubuntu | описание релиза из истории, создание релиза с четырьмя файлами |

Сверка «тег совпадает с кодом» есть только здесь: `release.sh` ее сделать не может, он тег и
создает. При расхождении сборки не будет.

Что проверяется у собранной программы:

- **Windows**: размер exe и версия в его свойствах (вкладка «Подробно»).
- **macOS**: версия в `Info.plist`, архитектура (arm64 или x86_64) и подпись.
- **Linux**: исполняемый файл ELF нужного размера.
- **Упаковка**: образ `.dmg` монтируется, и в нем проверяются бит запуска и подпись; в `tar.gz`
  ровно один файл, с битом запуска.
- **Везде**: программа запускается и работает несколько секунд. Признак запуска — строка
  с путем к `settings.ini` в журнале. Это ловит то, чего не видно по тестам: модуль или
  библиотеку, которую PyInstaller не положил в сборку. На Linux проверка идет на виртуальном
  экране Xvfb, то есть с тем же модулем экрана xcb, что у пользователя.

Право записи в репозиторий есть только у этапа публикации. Публикует предустановленный на
машине GitHub `gh`, стороннего кода с доступом к репозиторию в цепочке нет.

### Машины сборки

| Файл | Машина | Почему |
| --- | --- | --- |
| Windows | `windows-latest` | |
| Linux | `ubuntu-22.04` | программа запускается на системах не старше той, на которой собрана (glibc 2.35). Когда GitHub уберет 22.04, перейти на `ubuntu-24.04` |
| macOS Apple Silicon | `macos-latest` | |
| macOS Intel | `macos-15-intel` | PyInstaller собирает только под архитектуру своей машины. Intel-машины GitHub обещает держать до августа 2027, после этого останется только Apple Silicon |

Сборка описана в [BackupApp.spec](../BackupApp.spec): на Windows и Linux один файл без окна
консоли, на macOS приложение `BackupApp.app`, потому что программа для macOS всегда
папка-бандл. Номер версии spec берет из `constants.py`.

## Файлы релиза

| Файл | Что внутри |
| --- | --- |
| `BackupApp-9.0.1-windows-x64.exe` | сама программа, без архива: скачал и запустил |
| `BackupApp-9.0.1-macos-arm64.dmg` | `BackupApp.app` и ярлык папки «Программы» |
| `BackupApp-9.0.1-macos-x64.dmg` | то же для Intel |
| `BackupApp-9.0.1-linux-x64.tar.gz` | один файл `BackupApp` |

- **Windows.** Exe без архива, чтобы сразу запускать. Обратная сторона: автозапуск помнит
  путь к файлу, а у каждой версии свое имя, поэтому после обновления автозапуск нужно включить
  заново. Об этом сказано в описании каждого релиза.
- **macOS.** Образ `.dmg`: установка — перетащить программу на ярлык «Программы». Внутри
  образа программа с ad-hoc подписью: без нее Apple Silicon не запустит программу вовсе,
  а с ней macOS пишет «не удалось проверить», и запуск разрешается в настройках.
- **Linux.** `tar.gz`, а не zip: zip теряет бит запуска, и распакованная программа
  не запустилась бы.

Программа не подписана платным сертификатом, поэтому Windows и macOS при первом запуске
просят подтверждение. Что нажать, написано в описании каждого релиза. Описание собирает
[release-notes.sh](../scripts/github-release/release-notes.sh) из секции версии в истории
релизов. Описание выпущенной версии:

```bash
scripts/github-release/release-notes.sh 9.0.1
```

До выпуска будущее описание показывает `release-notes.sh "Не выпущено"`: в именах файлов вместо
номера будет «Не выпущено».

## Если что-то пошло не так

### Пересобрать файлы, не двигая тег

Когда код правильный, а сломалась сама сборка (сбой машины GitHub, поправили `release.yml`):
**Actions → Release → Run workflow**, поле `tag` = `v9.0.1`. Релиз обновится, файлы
перезапишутся, тег останется на месте. При ручном запуске из `master` берется только сам
`release.yml`, а код, `BackupApp.spec` и скрипты — из тега: если чинили их, нужен перевыпуск.

Кнопка «Re-run failed jobs» на упавшем прогоне тоже подходит, но берет `release.yml` из
коммита под тегом. Если чинили сам `release.yml`, нужен ручной запуск или перевыпуск.
Собранные файлы хранятся сутки: если упала только публикация, «Re-run failed jobs» поможет
в течение суток, позже — «Re-run all jobs» или ручной запуск.

### Перевыпустить ту же версию

Когда в релизе нашлась ошибка, а версией еще никто не пользуется:

```bash
# 1. Удалить релиз на GitHub: страница релиза, кнопка с корзиной.
#    Без этого новый прогон обновит старый релиз: заменит файлы и описание.

# 2. Поправить код, закоммитить, отправить и дождаться зеленых тестов (Actions → Tests):
git push origin master

# 3. Снять старый тег, поставить заново и запустить сборку:
git push --delete origin v9.0.1 2>/dev/null; git tag -d v9.0.1 2>/dev/null; git tag -a v9.0.1 -m "BackupApp 9.0.1" && git push origin v9.0.1
```

Первые команды шага 3 разделены `;`, а не `&&`: удаление тега, которого на GitHub уже нет,
не должно обрывать цепочку. Последние две соединены `&&`: если тег не создался, отправлять нечего.

### Отменить релиз

Удалить релиз на GitHub, затем снять тег:

```bash
git push --delete origin v9.0.1
git tag -d v9.0.1
```

Только если версию еще никто не скачал: иначе у людей останутся битые ссылки.

### Черновик

При ручном запуске есть галочка `draft`. Черновик видят только те, у кого есть право записи
в репозиторий: посетитель на странице релизов его не увидит. Опубликовать черновик можно
кнопкой **Edit → Publish release** или повторным ручным запуском без галочки `draft`.
Последняя строка шага публикации показывает, черновик ли получился:

```
черновик: false  https://github.com/rvburov/backup-desktop-app/releases/tag/v9.0.1
```

### Защита тегов

Опубликованный релиз привязан к тегу. Чтобы тег нельзя было сдвинуть или удалить по ошибке,
включите защиту: **Settings → Rules → Rulesets → New tag ruleset**, шаблон `v*`, галочки
**Restrict updates** и **Restrict deletions**. С ней команды из разделов «Перевыпустить ту же
версию» и «Отменить релиз» не пройдут: добавьте себя в **Bypass list** правила или выключайте
его на время.

### Тесты скриптов выпуска

```bash
scripts/github-release/release-test.sh
```

Нужны bash и git 2.28 или новее, в Git Bash на Windows есть все остальное. `release.sh`
проверяется по-настоящему, вплоть до коммита, тега и
push, но в одноразовой копии проекта со своим «GitHub» во временной папке. Настоящий
репозиторий прогон не меняет, это тоже проверяется. Тесты идут в
[tests.yml](../.github/workflows/tests.yml) на Windows, Linux и macOS. Если установлен
`actionlint`, заодно проверяется весь `release.yml`.
